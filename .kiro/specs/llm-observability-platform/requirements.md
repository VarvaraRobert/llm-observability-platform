# Requirements Document

## Introduction

The LLM Observability Platform (MVP) is a small, self-hostable system that lets developers inspect the internal behavior of their LLM applications. It captures every request, agent step, and tool call as structured trace data, along with cost and latency, and presents it in a dashboard. It is a minimal alternative to tools such as LangSmith or Langfuse.

The platform has three components: a Python SDK that instruments application code and sends traces asynchronously, a FastAPI + PostgreSQL backend that ingests, validates, stores, and serves trace data with per-project API-key authentication, and a React dashboard that lists traces and renders each trace as a tree of spans with per-span and per-trace cost and latency.

This document defines the requirements for the MVP. Evaluation datasets, LLM-as-judge scoring, CI integration, alerting, multi-user accounts, and data masking are explicitly out of scope.

## Glossary

- **Platform**: The complete LLM Observability Platform, comprising the SDK, Backend, and Dashboard.
- **SDK**: The Python library that instruments host application code and transmits trace data to the Backend.
- **Host_Application**: The developer's LLM application that imports and uses the SDK.
- **Backend**: The FastAPI service, backed by PostgreSQL, that provides the ingestion endpoint, the query API, and authentication.
- **Dashboard**: The React + TypeScript web client that displays traces and spans.
- **Database**: The PostgreSQL instance used by the Backend to persist projects, traces, and spans.
- **Project**: A logical grouping of traces owned by a developer, identified by a unique identifier and associated with one API key.
- **API_Key**: A secret credential associated with exactly one Project, used to authenticate ingestion and query requests.
- **Trace**: A single end-to-end execution recorded by the SDK, belonging to one Project, and containing one or more Spans.
- **Span**: A single unit of work within a Trace. A Span has a name, a type, input, output, start time, end time, status, error, model, prompt token count, completion token count, computed cost, and metadata. Spans form a tree within a Trace via a parent span reference.
- **Root_Span**: A Span within a Trace that has no parent span reference.
- **Span_Type**: The classification of a Span; one of `llm`, `tool`, `agent`, or `other`.
- **Span_Status**: The completion state of a Span; one of `success` or `error`.
- **Parent_Span_Id**: A reference on a Span that identifies another Span in the same Trace as its parent; absent for a Root_Span.
- **Span_Tree**: The hierarchical structure formed by the parent span references of all Spans within a Trace.
- **Price_Table**: A configurable mapping from a model identifier to per-token prices for prompt tokens and completion tokens, used to compute Span cost.
- **Cost**: The monetary cost of a Span, computed from the Span token counts and the Price_Table.
- **Latency**: The elapsed wall-clock time of a Span or Trace, computed from start and end times.
- **Trace_Latency**: The elapsed wall-clock time of a Trace, computed as the difference between the latest Span end time and the earliest Span start time across all Spans in the Trace.
- **Trace_Status**: The derived status of a Trace; `error` if any Span in the Trace has Span_Status `error`, otherwise `success`.
- **Trace_Id**: A unique identifier for a Trace, generated by the SDK.
- **Span_Id**: A unique identifier for a Span, generated by the SDK and unique within its Trace.
- **Admin_CLI**: A command-line script, run by an operator, that creates Projects and issues API keys.
- **Api_Key_Hash**: The stored one-way hash of an API_Key; the Backend never stores the raw API_Key.
- **Ingestion_Endpoint**: The Backend HTTP endpoint that receives trace data from the SDK.
- **Query_API**: The set of Backend HTTP endpoints that the Dashboard uses to read projects, traces, and spans.
- **Trace_List**: The Dashboard view that displays multiple traces for a Project.
- **Trace_Detail**: The Dashboard view that displays a single Trace as a Span_Tree.
- **Compose_Setup**: The Docker Compose configuration that runs the Backend, Database, and Dashboard locally.

## Requirements

### Requirement 1: SDK Instrumentation API

**User Story:** As a developer, I want to instrument my LLM application code with a decorator and an LLM-call wrapper, so that I can record traces without rewriting my application logic.

#### Acceptance Criteria

1. THE SDK SHALL provide a decorator that records the decorated function execution as a Span within the current Trace.
2. THE SDK SHALL provide a wrapper for LLM calls that records the call as a Span with Span_Type `llm`.
3. WHEN a decorated function or wrapped LLM call executes while no Trace is active, THE SDK SHALL start a new Trace and record the Span as the Root_Span of that Trace.
4. WHEN a decorated function or wrapped LLM call executes while a Trace is active, THE SDK SHALL record the Span as a child of the currently active Span by setting the Parent_Span_Id to the active Span identifier, and SHALL restore the previously active Span when the recorded Span ends.
5. WHEN a decorated function or wrapped LLM call completes without raising an error, THE SDK SHALL capture the Span name, Span_Type, input, output, start time, end time, and set the Span_Status to `success`.
6. IF a decorated function or wrapped LLM call raises an error, THEN THE SDK SHALL set the Span_Status to `error`, capture the error as the Span error, record the Span end time, and re-raise the error to the Host_Application.
7. WHEN a wrapped LLM call completes and the call reports a model identifier and token counts, THE SDK SHALL capture the model identifier, prompt token count, and completion token count.
8. IF a wrapped LLM call completes without reporting a model identifier or token counts, THEN THE SDK SHALL leave those values absent on the Span and SHALL record the Span without failing the Host_Application.
9. THE SDK SHALL generate a unique Trace_Id when it starts a new Trace and a unique Span_Id for each Span it records.
10. WHEN a decorated function or wrapped LLM call executes within asynchronous code or across threads, THE SDK SHALL propagate the active Trace and active Span using context-local storage so that each Span is attributed to the correct parent regardless of async task or thread boundaries.

### Requirement 2: SDK Non-Blocking and Resilient Transmission

**User Story:** As a developer, I want the SDK to send traces asynchronously and tolerate backend outages, so that observability never breaks or slows my application.

#### Acceptance Criteria

1. WHEN the SDK records a Span, THE SDK SHALL place the Span data into a bounded in-memory queue and return control to the Host_Application execution path without waiting for transmission to the Ingestion_Endpoint to complete.
2. THE SDK SHALL transmit enqueued Spans to the Ingestion_Endpoint in batches, sending a batch when the number of enqueued Spans reaches a configurable batch size (default 100 Spans, range 1 to 1000) or when a configurable flush interval elapses (default 5 seconds, range 1 to 60 seconds), whichever occurs first.
3. IF the Backend is unreachable when the SDK attempts transmission, THEN THE SDK SHALL retain the affected Span data in the bounded queue and allow the Host_Application to continue execution.
4. IF the bounded queue is full when the SDK attempts to enqueue a Span, THEN THE SDK SHALL discard the oldest enqueued Span data to make room for the new Span and allow the Host_Application to continue execution, where the queue capacity is configurable (default 10000 Spans, range 100 to 100000).
5. IF transmission of a batch to the Ingestion_Endpoint fails, THEN THE SDK SHALL retry transmission of that batch up to a configurable maximum number of retry attempts (default 3, range 0 to 10) and SHALL discard the batch after the final attempt fails, and SHALL allow the Host_Application to continue execution.
6. IF an error occurs within the SDK transmission path, THEN THE SDK SHALL suppress the error from the Host_Application execution path and allow the Host_Application to continue execution.
7. WHEN the SDK transmits a batch, THE SDK SHALL include the API_Key for authentication with the Backend.
8. WHEN the Host_Application process begins to exit, THE SDK SHALL attempt to flush all enqueued Spans to the Ingestion_Endpoint within a configurable shutdown timeout (default 5 seconds) and SHALL allow the process to exit whether or not the flush completes.

### Requirement 3: Trace Ingestion

**User Story:** As a developer, I want the backend to accept, validate, and store traces from the SDK, so that my recorded data is persisted for later inspection.

#### Acceptance Criteria

1. THE Backend SHALL expose an Ingestion_Endpoint that accepts Trace data containing between 1 and 1000 Spans in a single request.
2. WHEN the Ingestion_Endpoint receives a request with a valid API_Key, THE Backend SHALL associate the received Trace with the Project identified by that API_Key.
3. IF the Ingestion_Endpoint receives a request with a missing or invalid API_Key, THEN THE Backend SHALL reject the request with an HTTP 401 status and SHALL NOT persist any data from the request.
4. WHEN the Ingestion_Endpoint receives Trace data, THE Backend SHALL validate that the Trace includes an SDK-generated Trace_Id, that each Span includes an SDK-generated Span_Id, a non-empty name, a Span_Type that is one of `llm`, `tool`, `agent`, or `other`, a start time, an end time that is greater than or equal to the start time, and a Span_Status that is one of `success` or `error`.
5. IF a received Span fails validation, THEN THE Backend SHALL reject the request with an HTTP 422 status and an error message indicating which Span and which field failed validation, and SHALL NOT persist any Span from the request.
6. WHEN the Ingestion_Endpoint receives a valid Trace, THE Backend SHALL persist the Trace and all contained Spans to the Database as a single atomic operation, preserving each Parent_Span_Id, such that either all Spans are persisted or none are persisted.
7. WHEN the Backend persists a Span with Span_Type `llm` that includes a model identifier and token counts, THE Backend SHALL compute and store the Span Cost using the Price_Table.
8. WHEN the Backend has persisted a valid Trace, THE Backend SHALL respond with an HTTP 2xx status.
9. IF the Ingestion_Endpoint receives a request whose body cannot be parsed as Trace data or that contains more than 1000 Spans, THEN THE Backend SHALL reject the request with an HTTP 400 status and an error message indicating the reason, and SHALL NOT persist any data from the request.
10. WHEN the Ingestion_Endpoint receives a Span whose Span_Id already exists for the Trace identified by the request, THE Backend SHALL ignore the duplicate Span and SHALL NOT create a second stored copy, and SHALL respond with an HTTP 2xx status.
11. IF a received Span has an input or output whose serialized size exceeds a configurable maximum payload size (default 64 KB per field), THEN THE Backend SHALL reject the request with an HTTP 413 status and an error message indicating which Span and field exceeded the limit, and SHALL NOT persist any Span from the request.

### Requirement 4: Cost Computation

**User Story:** As a developer, I want span cost computed from a configurable price table, so that I can see what each model call and each trace costs me.

#### Acceptance Criteria

1. THE Backend SHALL load a Price_Table that maps each model identifier to a non-negative per-prompt-token price and a non-negative per-completion-token price, and SHALL store Span Cost and Trace Cost using decimal precision (not binary floating point) to avoid rounding drift.
2. WHEN the Backend computes the Cost of a Span whose model identifier has an entry in the Price_Table and whose prompt token count and completion token count are both present, THE Backend SHALL calculate the Cost as the prompt token count multiplied by the per-prompt-token price plus the completion token count multiplied by the per-completion-token price for the Span model identifier.
3. IF the Price_Table contains no entry for a Span model identifier, THEN THE Backend SHALL store the Span Cost as zero AND SHALL record a flag indicating the price is unknown for that model so that the Dashboard can display "unknown price".
4. IF a Span has no model identifier or is missing a prompt token count or completion token count, THEN THE Backend SHALL store the Span Cost as zero.
5. WHEN the Backend computes the Cost of a Trace, THE Backend SHALL calculate the Trace Cost as the sum of the Cost values of all Spans in the Trace, which is zero when the Trace has no Spans with a non-zero Cost.
6. WHERE the Price_Table is updated in configuration, THE Backend SHALL apply the updated prices to Spans ingested after the update and SHALL leave the stored Cost of Spans ingested before the update unchanged.

### Requirement 5: Trace and Span Query API

**User Story:** As a developer, I want a query API that returns my traces and their spans, so that the dashboard can display what happened inside my application.

#### Acceptance Criteria

1. THE Backend SHALL expose a Query_API that returns a list of Traces for the Project identified by the request API_Key, ordered by Trace start time in descending order, limited to a configurable page size (default 50, maximum 100) per response, and SHALL return a continuation token when more Traces are available.
2. IF a Query_API request has a missing or invalid API_Key, THEN THE Backend SHALL reject the request with an HTTP 401 status and return no Trace data.
3. WHEN the Query_API returns a Trace list, THE Backend SHALL include for each Trace the Trace identifier, start time, end time, Span_Status, computed Trace Cost, and computed Trace Latency.
4. WHEN the Query_API receives a request to filter Traces by Span_Status, THE Backend SHALL return only Traces whose status matches the requested Span_Status.
5. IF the Query_API receives a request to filter by a Span_Status value that is not a recognized Span_Status, THEN THE Backend SHALL reject the request with an HTTP 400 status and an error indication specifying the invalid filter value.
6. WHEN the Query_API receives a request to filter Traces by a time range with a start bound and an end bound, THE Backend SHALL return only Traces whose start time is greater than or equal to the start bound and less than or equal to the end bound.
7. IF the Query_API receives a request to filter by a time range in which the start bound is later than the end bound, or either bound is not a valid timestamp, THEN THE Backend SHALL reject the request with an HTTP 400 status and an error indication specifying the invalid time range.
8. WHEN the Query_API receives a request for a single Trace by identifier, THE Backend SHALL return all Spans of that Trace, including each Span name, Span_Type, input, output, start time, end time, Span_Status, error, model identifier, prompt token count, completion token count, Cost, Parent_Span_Id, and metadata.
9. IF the Query_API receives a request for a Trace identifier that does not belong to the Project identified by the request API_Key, THEN THE Backend SHALL respond with an HTTP 404 status.
10. IF the Query_API receives a request for a Trace identifier that does not exist, THEN THE Backend SHALL respond with an HTTP 404 status.
11. WHEN the Query_API receives a request with a continuation token, THE Backend SHALL return the next page of Traces following the position indicated by that token.
12. WHEN the Query_API returns a Trace, THE Backend SHALL compute Trace_Status as `error` if any Span in the Trace has Span_Status `error` and otherwise `success`, and SHALL compute Trace_Latency as the difference between the latest Span end time and the earliest Span start time in the Trace.

### Requirement 6: Project and API-Key Authentication

**User Story:** As a developer, I want each project protected by its own API key, so that only authorized callers can send and read that project's traces.

#### Acceptance Criteria

1. THE Backend SHALL associate each Project with exactly one active API_Key by storing only the Api_Key_Hash and SHALL never store the raw API_Key.
2. WHEN the Backend receives a request, THE Backend SHALL extract the API_Key from the request authorization header.
3. IF the Backend receives a request that contains no API_Key, THEN THE Backend SHALL reject the request with an HTTP 401 status and an error indicating that authentication credentials are missing.
4. WHEN the Backend receives a request containing an API_Key, THE Backend SHALL resolve the Project by hashing the presented API_Key and matching the resulting Api_Key_Hash against the stored Api_Key_Hash before processing the request.
5. IF the Backend receives a request whose API_Key matches no active Project, THEN THE Backend SHALL reject the request with an HTTP 401 status and an error indicating that the credentials are invalid, without disclosing whether the API_Key or the Project is the cause.
6. WHEN the Backend processes an authenticated request, THE Backend SHALL restrict the request to Traces and Spans belonging to the Project resolved from the API_Key.
7. IF an authenticated request references a Trace or Span belonging to a Project other than the one resolved from the API_Key, THEN THE Backend SHALL reject the request with an HTTP 404 status and SHALL NOT return the referenced Trace or Span data.

### Requirement 7: Project and API-Key Provisioning

**User Story:** As an operator, I want a CLI script to create projects and issue API keys, so that I can provision access without a separate admin UI.

#### Acceptance Criteria

1. THE Admin_CLI SHALL provide a command that creates a new Project with a unique identifier.
2. WHEN the Admin_CLI creates a Project, THE Admin_CLI SHALL generate a new API_Key, store only its Api_Key_Hash in the Database, and output the raw API_Key to the operator exactly once.
3. THE Admin_CLI SHALL NOT store or log the raw API_Key after displaying it.
4. IF the Admin_CLI is asked to create a Project with an identifier that already exists, THEN THE Admin_CLI SHALL report an error and SHALL NOT create a duplicate Project.

### Requirement 8: Dashboard Trace List

**User Story:** As a developer, I want a dashboard that lists my traces with filters, so that I can find the executions I care about.

#### Acceptance Criteria

1. THE Dashboard SHALL display a Trace_List that shows, for each Trace, the Trace identifier, start time, Span_Status, Trace Cost, and Trace Latency, ordered by start time from most recent to least recent.
2. WHEN a developer opens the Dashboard, THE Dashboard SHALL prompt for an API_Key before displaying any Trace data.
3. WHEN a developer has entered an API_Key, THE Dashboard SHALL display only Traces belonging to the Project resolved from the entered API_Key.
4. WHEN a developer applies a Span_Status filter in the Dashboard, THE Dashboard SHALL display only Traces whose status matches the selected Span_Status.
5. WHEN a developer applies a time-range filter in the Dashboard, THE Dashboard SHALL display only Traces whose start time falls within the selected time range.
6. WHEN a developer applies both a Span_Status filter and a time-range filter in the Dashboard, THE Dashboard SHALL display only Traces that satisfy both filters.
7. WHEN the set of Traces that satisfies the resolved Project and active filters is empty, THE Dashboard SHALL display an empty-state indication that no Traces match and SHALL display no Trace rows.
8. IF the Dashboard fails to retrieve Traces from the Query_API, THEN THE Dashboard SHALL display an error indication that Traces could not be loaded and SHALL retain the entered API_Key and filter selections.
9. WHEN more Traces are available than fit in one page, THE Dashboard SHALL allow the developer to load the next page using the continuation token from the Query_API.
10. WHEN a developer selects a Trace in the Trace_List, THE Dashboard SHALL open the Trace_Detail view for that Trace.

### Requirement 9: Dashboard Trace Detail and Span Tree

**User Story:** As a developer, I want to see a trace as a tree of spans with cost and latency, so that I can understand each step and spot slow or expensive operations.

#### Acceptance Criteria

1. WHEN the Dashboard opens the Trace_Detail view for a Trace, THE Dashboard SHALL reconstruct the Span_Tree from the Parent_Span_Id of each Span.
2. IF the Dashboard fails to retrieve the requested Trace from the Query_API, THEN THE Dashboard SHALL display an error indication that the Trace could not be loaded and SHALL NOT render a Span_Tree.
3. THE Dashboard SHALL render the Span_Tree with each child Span displayed beneath its parent Span.
4. WHEN the Dashboard renders a Span in the Trace_Detail view, THE Dashboard SHALL display the Span name, Span_Type, Span_Status, Span Latency, and Span Cost.
5. THE Trace_Detail view SHALL display the Trace Cost and the Trace Latency for the Trace.
6. WHILE no Span is selected in the Trace_Detail view, THE Dashboard SHALL display no Span detail panel.
7. WHEN a developer selects a Span in the Trace_Detail view, THE Dashboard SHALL display the Span input, output, model identifier, prompt token count, completion token count, error, and metadata, and SHALL indicate any of these fields that are absent on the selected Span.
8. IF a Span has Span_Status `error`, THEN THE Dashboard SHALL display the Span error for that Span.
9. WHERE a Span's model is absent from the Price_Table (price-unknown flag set), THE Dashboard SHALL display "unknown price" in place of the Span Cost for that Span.

### Requirement 10: Span-Tree Reconstruction Integrity

**User Story:** As a developer, I want the span tree to be reconstructed correctly from stored data, so that the displayed hierarchy matches what my application actually did.

#### Acceptance Criteria

1. WHEN the Span_Tree is reconstructed for a Trace, THE Platform SHALL place each non-root Span as a child of the Span identified by its Parent_Span_Id.
2. WHEN the Span_Tree is reconstructed for a Trace, THE Platform SHALL include every Span of the Trace in the reconstructed Span_Tree exactly once.
3. WHEN the Span_Tree is reconstructed for a Trace, THE Platform SHALL identify as a Root_Span every Span whose Parent_Span_Id is absent, and SHALL include every such Root_Span in the reconstructed Span_Tree.
4. IF a Span references a Parent_Span_Id that does not correspond to any Span in the same Trace, THEN THE Platform SHALL treat that Span as a Root_Span of the reconstructed Span_Tree.
5. IF a Span's Parent_Span_Id equals that Span's own identifier, THEN THE Platform SHALL treat that Span as a Root_Span of the reconstructed Span_Tree.
6. IF following the Parent_Span_Id references from a Span would revisit a Span already on its ancestor chain, THEN THE Platform SHALL treat the first Span on that chain whose parent is already an ancestor as a Root_Span of the reconstructed Span_Tree, so that the reconstructed Span_Tree contains no cycles.
7. WHEN a reconstructed parent Span has more than one child Span, THE Platform SHALL order those child Spans by ascending Span start time, and SHALL break ties between equal start times by ascending Span identifier.

### Requirement 11: Local Deployment with Docker Compose

**User Story:** As a developer, I want to run the whole platform locally with Docker Compose, so that I can self-host it without manual setup of each component.

#### Acceptance Criteria

1. THE Compose_Setup SHALL define services for the Backend, the Database, and the Dashboard.
2. WHEN a developer starts the Compose_Setup, THE Platform SHALL start the Backend, the Database, and the Dashboard and SHALL report each service as ready within 120 seconds.
3. IF any one of the Backend, the Database, or the Dashboard fails to reach a ready state within 120 seconds of startup, THEN THE Platform SHALL report the name of each service that failed to start and the reason for the failure.
4. WHEN the Compose_Setup starts the Backend for the first time against an empty Database, THE Backend SHALL create the schema required for Projects, Traces, and Spans before accepting requests on the Ingestion_Endpoint or the Query_API.
5. IF the Backend fails to create the required schema against an empty Database, THEN THE Backend SHALL report an error indicating schema creation failed, SHALL leave the Database with no partially created schema, and SHALL NOT accept requests on the Ingestion_Endpoint or the Query_API.
6. WHILE the Compose_Setup is running with all services reported as ready, THE SDK SHALL be able to reach the Ingestion_Endpoint and the Dashboard SHALL be able to reach the Query_API.

### Requirement 12: Quality and Verification

**User Story:** As a maintainer, I want automated tests and documented design decisions, so that the platform is correct and its rationale is traceable.

#### Acceptance Criteria

1. THE Platform SHALL include automated tests that verify valid Trace ingestion persists the Trace and that invalid Trace ingestion is rejected, covering at minimum valid payloads, missing required fields, and malformed payloads.
2. WHEN a Trace fails ingestion validation, THE Platform SHALL include an automated test that asserts the Trace is not persisted and a validation error indicating the failed field is returned.
3. THE Platform SHALL include automated tests that verify Cost computation from the Price_Table produces the expected cost for a known Trace within a tolerance of 0.0001 currency units, covering at minimum one in-table model and one input/output token split.
4. IF Cost computation references a model absent from the Price_Table, THEN THE Platform SHALL include an automated test that asserts the Span Cost is stored as zero and the absent model is recorded.
5. THE Platform SHALL include automated tests that verify Span_Tree reconstruction produces a tree whose parent-child links and span ordering match the expected structure, covering at minimum a single-span trace, a multi-level nested trace, and a span referencing a missing parent.
6. THE Platform SHALL include an automated test that verifies ingesting a Span whose Span_Id already exists for a Trace does not create a second stored copy and returns an HTTP 2xx status.
7. THE Platform SHALL achieve a passing result on all automated tests described in criteria 1 through 6 before any build is considered complete.
8. WHEN a design decision is made for the Platform, THE maintainer SHALL record the decision as an Architecture Decision Record in the `docs/adr/` directory within the same change set that implements the decision.
